# Android recorder 0.5.33 — local test candidate

Updated 2026-11-02, Asia/Manila. APK version 0.5.33, version code 39. No Git commit, GitHub push or web deployment was performed for this update.

## Player and staff workflow

1. Enroll into the device's existing Admin entry. Updating with `adb install -r` preserves app data. Uninstalling erases private enrollment and unsent private files; a Gallery/Files export is a separate user-owned copy. Re-enroll into the same Admin entry after reinstalling instead of creating another entry.
2. After app launch or USB camera reconnect, complete the camera check before entering player addresses. The test records extra source footage and creates a full three-second branded preview. Play the clip and confirm picture and sound. A server's previous test approval does not bypass the current app launch's check. Camera configuration changes also invalidate approval. Subsequent matches in the same configured launch reuse the confirmation.
3. A matching camera USB microphone takes priority when Android exposes it. Otherwise the app selects the phone/tablet microphone. The camera review and recording message identify the source. Admin Device details shows the last reported microphone, model, Android/API version, APK/build and attached USB camera names. Attachment and historical reports are not proof of current camera health. Android 8's Camera2/MediaRecorder path cannot always report a live route; the label explicitly says when routing is unreported. The direct UVC path uses AudioRecord routing APIs available on the supported minimum SDK.
4. Tap the welcome screen, manually enter up to four player addresses, add them, review the recipients, and start. The capture is prepared before 3–2–1. The visible recording timer counts **00:00 upward** to the configured maximum. Repeated stop requests remain safe.
5. After stop, the completed capture's duration and file details are persisted before network release. The foreground camera becomes free; saved-video branding/upload proceeds separately. Another group can enter addresses while an earlier upload runs, subject to the server confirming capture release. An offline server cannot grant a new session.
6. In **Saved videos**, names show recording date/time and the first recipient, plus `+N more` for additional recipients. Full technical recording ID is in Details and remains usable in Admin logs. Export names use date/time and a bounded recipient label. Older local records acquire recipient metadata from their authenticated server queue when available; missing player details are never guessed from a newer group.
7. **Adding logo…** hides/unloads the preview and shows a processing indicator. The private playback endpoint also refuses previews while branding is active. Once complete, the player loads the branded file. Failed originals remain exportable for inspection. Preview and seeking use the full input stream because WebView applies its own requested byte offset.
8. Choose **Save to device** to create a separate copy in Movies/DinkVision (Gallery/Files on Android 10+; Android's save picker on Android 8/9). Choose **Retry processing** or **Retry upload** for a failed owned video. Automatic retries retain the existing bounded retry/backoff policy; manual retry restarts the budget for that same recording and recipient group. Clips under one minute remain local and are not uploaded/emailed.
9. Branding keeps the original while writing a temporary output. On restart, an interrupted safe swap is restored first, then the queue checks local files. An interrupted processing flag becomes resumable work. A missing original becomes unavailable/failed and is reported to Admin, not retried endlessly. Active branding refreshes file-presence reports. Admin changes an old processing report to **Waiting for device · file check pending** after 45 seconds without a fresh report. It cannot inspect a powered-off tablet remotely.
10. Once Google Drive upload is verified, the private upload copy is released. Previously exported Gallery copies remain. Email delivery is tracked independently by the backend. Admin date/player labels link to the exact recording log, including older sessions outside the latest 100.

## Registration and Admin consistency

Re-enrolling the same Admin entry rotates its credential in place, preserving kiosk/session ownership and the local queue. It no longer deactivates its own renewed registration. Moving an authenticated app registration to a different Admin entry disables the old active registration atomically. Moving away from an entry with unfinished footage is blocked. Historical rows/recording logs are retained; devices of the same model are not automatically merged.

Admin confirms live recording only with a recent capture report and within its configured duration plus grace. Old disconnected captures display **Recording unconfirmed**. The Renzo court tablet's old session and footage were not cancelled, deleted or re-enrolled during these tests.

The existing Supabase migration runner applied the new optional `browser_devices.device_info` JSON field and the atomic re-enrollment overload. Both were first exercised in isolated database tests. Existing RLS/role boundaries remain. The local backend accepts older inventory-free APK heartbeats, and the APK's optional inventory report remains compatible with an older backend. Supabase MCP OAuth configuration completed; this running tool session did not expose MCP database tools, so verification used the repository's configured database access.
